# Java 地图路径检查练习：把优化前的双重循环交给你

这是一个独立的本地练习，模拟项目中“检查地图中哪些路径相交或贴得太近”的问题。**没有连接真实车辆、Gateway 或现场地图，也不需要修改业务仓库源码。**

你会看到一个已经可以工作的旧实现。你的任务是先理解它，再自己把其中“对所有路径两两做精确判断”改成更聪明的候选筛选。可以借鉴项目里的包围盒和扫描思路，但我没有把优化答案预先写进你的工作区。

## 1. 你最终要做什么？

只需要先关注这一个文件：

**[MyPathChecker.java](src/lab/MyPathChecker.java)**

现在它的核心是：

```java
for (int i = 0; i < paths.size(); i++) {
    for (int j = i + 1; j < paths.size(); j++) {
        MapPath first = paths.get(i);
        MapPath second = paths.get(j);

        exactChecks++;
        if (Geometry.conflicts(first, second)) {
            conflicts.add(new Conflict(first.id(), second.id()));
        }
    }
}
```

`Geometry.conflicts()` 已经写好，负责判断两条线段是否相交或距离不超过 3 厘米。你不需要先学懂它里面所有几何公式。

你的目标：**保持最终冲突结果和顺序与旧版一致，同时尽量减少真正调用 `Geometry.conflicts()` 的次数。** 你可以增加辅助类、`Map`、`List`、排序或其他 Java 数据结构；是否使用循环不是目的，重点是避免无必要的精确判断。

`exactChecks` 必须如实统计你实际调用 `Geometry.conflicts()` 的次数，不能为了通过测试手动填小数字。

## 2. 文件都是什么？

```text
src/lab/
├── Point.java                 坐标点
├── MapPath.java               一条路径：ID、起点、终点
├── Conflict.java              一对存在问题的路径
├── CheckResult.java           冲突列表与精确判断次数
├── PathChecker.java           所有检查器遵守的接口
├── Geometry.java              已写好的精确几何判断
├── ReferencePathChecker.java  保留原始双重循环的参考实现
├── MyPathChecker.java         你要修改的代码，初始也是双重循环
├── ExampleMaps.java           构造几张用于练习的假地图
├── PathCheckerTest.java       正确性及优化目标测试
└── MapLabApp.java             可选的图形界面
```

建议第一遍只看 `Point`、`MapPath`、`MyPathChecker` 和下面的例子。其余文件先当作项目里已经提供好的接口；需要追问时再逐个打开。`ReferencePathChecker` 是你对照的旧行为，请保留不改。

### 这个练习和真实项目有什么区别？

- 练习只处理**直线**；真实项目还会处理导入的曲线及采样折线。
- 本练习将线段相交、端点相接或线段最近距离不超过 3 厘米都视为冲突；真实项目的 `overlapAt()` 还有共享站点附近的忽略规则，距离判断实现也不完全相同。
- 为便于比较，本练习要求 `Conflict` 按原输入下标的双重循环顺序输出，且每条路径 ID 在同一张练习地图中唯一。
- 数据全部是本地构造的假数据。这里的耗时和检查次数不是项目现场性能数据。

## 4. 分两步验收，先正确，再看效果

### 第一步：正确性必须通过

```bash
java -cp out lab.PathCheckerTest
```

测试包括空地图、相交、远离、2 厘米、**恰好 3 厘米**、超过 3 厘米、端点相接、零长度路径、斜线，以及固定随机种子的地图。它还会将你的结果与独立的旧版参照比较，要求**内容和顺序一致**。

为什么要检查顺序？真实项目的优化也保留原路径顺序，以免原先排在前面的检查结果，因为空间排序发生无故变化。

如果测试报错，先读 `预期` 与 `实际`；如果差一对距离为 2 厘米的路径，检查你的筛选是否给 3 厘米的贴合阈值留了余量。如果路径对相同但顺序不同，检查你的空间排序与原输入下标。

### 第二步：再检查优化目标

```bash
java -cp out lab.PathCheckerTest --goal
```

测试会在一张 1000 条路径的分散练习地图上，对照旧版的 499,500 次精确判断，要求你的调用次数小于旧版的四分之一。**初始双重循环预期会报“优化目标尚未达到”**；这是刻意留下的任务。

这个目标是为了练习设计的，不是对所有地图的性能承诺。某些地图的盒子高度重叠，即使实现正确，候选数仍可能很多。测试统计精确判断次数，不是完整的算法耗时，也不能单凭它证明任何场景都更快。

## 6. 建议怎么动手？

不用一次想出完整方案。你可以分阶段完成，每一步都重新编译并跑正确性测试：

1. **先读旧循环**：拿文档的 A、B、C、D、E 五条线，列出旧版一共判断多少对，为什么不检查 A-A、也不会 A-B 再检查 B-A。
2. **先做简单粗筛**：对每条直线找两个端点的 `minX/maxX/minY/maxY`，当两个范围在某一轴上相距大于 3 厘米时跳过精确判断。可以暂时保留两个 `for`，先保证不漏结果。
3. **再尝试减少候选扫描**：考虑将盒子沿 x 或 y 轴排序；在什么条件下，后续盒子可以不用再看？想清楚 `break` 与 `continue` 的区别。
4. **保留原始顺序**：空间排序后记录原数组下标，想办法让最终冲突列表仍与旧版顺序相同。不要直接修改传入的 `paths` 列表，它可能是不可修改的。
5. **尝试边界**：将两条平行线的距离改成 0.02、0.03、0.031 米；再试斜线、端点相接、零长度线段。

你可以随时回看 [原项目包围盒六步详解](../../../../../personal/shiinapple.cn/blog/articles/amr-05.md)，但建议先自己画图、尝试，再对照源码。第 2 步即使仍有两个 `for`，只要精确调用次数下降也是有意义的第一步；第 3 步主要进一步减少扫描候选的工作。

## 7. 常见疑问

**“一定不能有两个 for 吗？”** 不是。AABB 粗筛也可能使用两个循环，关键是排序后能否提前结束，以及有多少对真正进入 `Geometry.conflicts()`；最坏情况下依然可能是平方级。

**“我的结果对了，为什么图上两条远处路径都变红？”** 界面只要发现某条路径参与了任意冲突，就把整条路径标红。它并没有显示哪两个端点有问题，具体路径对可以在测试里查看或自己扩展界面。

**“能不能自己改测试？”** 可以增加测试；建议保留原来的固定用例和 `ReferencePathChecker`，否则容易把错误实现误认为正确。

**“测的是实际 CPU 耗时吗？”** 测试的硬性优化目标是精确函数调用次数。GUI 会额外显示粗略耗时，但 JVM 预热、地图分布和机器负载都可能影响它。
