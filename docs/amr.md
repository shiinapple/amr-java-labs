# AMR 实习项目 · 从代码到面试

按“地图能不能用 → 路该怎么走 → 任务怎么发 → 编辑状态怎么保住”读即可。每节都先手算一个很小的输入，再回到现有练习跑一遍。练习里的站点、路线、日志均为本地教学数据。

## 1. 地图预检为什么先画包围盒？

**具体问题。** 一张地图有 1000 条路径。如果每两条都拿来精算相交、贴合等情况，要比较多少次？如果两条曲线相隔几十米，还需要精算吗？

**通俗解释。** 先用一个刚好罩住曲线的方框。两个盒子离得足够远，里面的线也不会碰到或者离得很近。盒子靠近时，才把线拿出来精算。

**正式概念。** AABB 是与坐标轴平行的包围盒，由 `minX, minY, maxX, maxY` 表示。粗筛允许多留一对，所以盒子相邻只说明“还要算”。粗筛漏掉一个真实冲突则会改变结果。若精算识别一定距离内的贴合，就要给比较条件留出同等间距与适当的浮点余量。

**完整示范。** 把阈值设成 0.05 米，三条水平线分别在 y=0、0.03、8，x 范围都是 [0, 10]。第一、第二条的盒间距离为 0.03，保留；第一、第三条相距 8，跳过；第二、第三条相距 7.97，也跳过。三对变成一对精算。如果在 x 或 y 的排序轴上，后面一个盒的最小值已经超过当前盒最大值加余量，后续同一方向的盒都可以停查。

练习里 1000 条全比较是 `1000 × 999 / 2 = 499500` 对。排序耗时随输入规模和数据分布变化，密集重叠时仍可能留下平方数量级的候选。课堂验收先看冲突结果是否一致，再看精算次数，最后才看机器实测耗时。代码回看位置是 `packages/shared-types/src/map-topology-check.ts` 的 `overlapCandidates` 与 `checkRoboshopMap`。展示缓存可以查 `services/mock-gateway/src/topology-preview-cache.ts`。 [地图检查练习](../java-map-check-lab/README.md) · [缓存与快照练习](../11-state-consistency-lab/README.md)

**独立练习。** 把第二条线移到 y=0.05 和 y=0.051，先预测粗筛候选，再用固定输入对照旧实现。另做一份所有盒子互相重叠的地图，记录粗筛剩下几对，解释为什么比稀疏地图更难优化。

## 2. 已经有两条可走路线，为什么选更长的？

**具体问题。** A 到 D 有一条 10 米直达路，以及 A → B → D 共 4 米的两段路。业务要求先比较段数，再比较距离，怎么选？

**通俗解释。** 先选换乘少的路线。只有换乘数一样时，才用总路程决定。同一个站还可能有两条并行边，回溯时要知道究竟走了哪条。

**正式概念。** 路网是有向图，邻接表存每个站的出边。堆里保存 `(段数, 距离, 节点)`，按前两项的字典序取最优。找到更好的代价时更新前驱站和边。若堆不支持原地更新，允许压入新候选，弹出后与当前最优代价核对，过期候选直接跳过。

**完整示范。**

```text
路线         代价 (段数, 米)
A → D       (1, 10)  ← 有直达边时选这里
A → B → D   (2,  4)  ← 删除直达边后选这里
A → C → D   (2,  5)
```

从 D 往前驱倒着找，得到边 `B-D`、`A-B`，反转后才是实际下发的顺序。这个策略用在简历所说的到点导航上。其他场景可能用距离优先，项目代码也有单独的距离最短路径实现。代码回看位置是 `packages/shared-types/src/min-hop-path.ts` 的 `minHopFixedPath`。 [有向图练习](../07-min-hop-path-lab/README.md)

**独立练习。** 删除 A → D，保留两条到 D 的路线，把 A → B 和 A → C 添加顺序互换，结果应保持 `A → B → D`。再反转唯一通往 D 的两条边，补测从 A 到 D 不可达。确认返回的边 ID 顺序和站序一致。

## 3. 控制器还没应答，为什么调度函数会进第二次？

**具体问题。** 调用 `pump` 发送第一批后进入 `await`。下一次调度周期又调用 `pump`。这时如果仍从原来的发送下标取路段，会发生什么？

**通俗解释。** 把“发过的货”和“已经签收的货”分开记。如果刚交给快递，还在等受理回执，需要先挂一张“正在处理”的单子。否则下一个人看到账本没变化，会再打一张相同的发货单。

**正式概念。** `sent` 表示已发送或暂时预占的边界，`done` 表示已完成的边界，`sending` 表示在途调用。网关在等待前设置标记，准备下发时预占发送边界，在明确失败或异常的本地分支回退计数，并在 `finally` 清理标记。收到命令的应答与走完路段的反馈有不同语义。

**完整示范。**

```text
控制器待应答前：sending=true，sent 从 0 预占到 2，done=0
第二次调度：    看到 sending=true，跳过重复发送
明确拒绝：      sent 回到 0，finally 清除 sending
重发后已接收：  sent=2，done=0
反馈到第 1 站： done 可以根据有效反馈推进到 1
```

在原项目看 `services/mock-gateway/src/route-run.ts` 的 `pump`。课堂 10 用可手动完成的 Future 复现竞态，保留基本不变量，但进度登记的具体时机和生产代码有简化。继续做 13 可以练原路线下标和回站交接。 [异步发送与恢复](../10-route-recovery-lab/README.md) · [断点交接](../13-checkpoint-handoff-lab/README.md)

**独立练习。** 保留第一次请求未完成，连续触发两次 `pump`，模拟控制器应只收到一批。再分别模拟明确拒绝和成功，检查下一次发送的起点，以及成功应答之前与之后的完成下标。

## 4. 删除失败时，为什么不能直接恢复整张旧图？

**具体问题。** A → B → C。用户删 B 时，页面先隐藏 B 和两条关联路径，请求稍后才返回。用户在等的时候新建了 D。如果删除被拒绝，把旧图整体恢复会怎样？

**通俗解释。** 撤回一次删站，只需找回这次删掉的对象。其他人的后续新增或你自己的别处编辑，应该保留。

**正式概念。** 乐观更新是先给出界面反馈，随后根据服务端结果确认或回滚。批量删除需要算关联路径、过滤在途 ID、按地图串行提交，失败时按当前状态恢复本批缺失对象。路径恢复前要确认端点存在。提交保存和撤销前也要理解它们与未结算删除的先后关系。

**完整示范。**

| 时刻 | 本地状态 | 正在处理 |
| --- | --- | --- |
| 初始 | A、B、C；A→B、B→C | 无 |
| 乐观删除 B | A、C；两条关联路径隐藏 | 删除 B 和两条路径 |
| 继续编辑 | A、C、D | 同上 |
| 删除失败 | A、B、C、D；补回有效关联路径 | 本批已结束 |

实习代码可查看 `apps/web-console/src/components/map-studio/map-delete.ts` 的 `planMapDeletion`、`withoutPendingDeletion`、`restoreDeleted`，服务端入口在 `services/mock-gateway/src/routes/maps.ts` 的 `POST /:id/delete-elements`。 [批量删除练习](../12-batch-delete-lab/README.md)

**独立练习。** 第一个批次删 B 未完成时，再发一次删除 B。对照假服务提交次数。第一批失败期间再新增 D 或更新 A，验证回滚不抹掉这次变化。若 C 已从当前状态移除，解释为什么不能恢复 B → C。

## 自测题

1. 两条路径的包围盒重叠，能直接报告路径冲突吗？如果大部分盒子重叠，性能结论要怎么说？
2. 按段数优先时，哪种输入最能区分“最少段数 BFS”和“同段数还选最短距离”的实现？
3. 控制器应答超时后，本地计数回退了。可以马上再发同一批吗？
4. 为什么批量删除失败要在当前状态上做局部恢复？如果某个被删对象已按同 ID 重新创建，该怎样处理？
5. 简历里的历史耗时和你今天跑的 Java 测试可以当成同一次实测吗？

## 答案与解析

1. 不能。盒重叠只是候选，真实关系要由原精算规则决定。密集数据会留下较多候选。先核对问题集合与顺序，再描述数据分布和实际耗时。
2. 两条段数相同但长度不同的路线，并故意把较长分支先放进邻接表。简单 BFS 仍能找到最少段数，但可能选中较长分支。
3. 先看超时的含义和控制器已接收的可能性。远端可能已执行。本地回退只改变本地账本。重发前需要可核对的设备状态、任务编号或协议支持的防重机制。
4. 请求等待期间还发生了其他编辑。判断线索是“当前是否仍缺这个 ID”。已存在的同 ID 对象应保留当前内容，路径还要核对端点。
5. 不能。简历记录的是一次历史离线曲线合成地图对照，约 44.2 秒到 58 毫秒。课堂的 1000 路径与候选计数来自另一份输入。复测时要记录数据、版本、机器、计时边界和结果一致性。
