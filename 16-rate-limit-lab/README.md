# 16 · 突然来了三个请求，网关先放几个？

对应简历里**流量治理与限流**的设计话题。本题实现一个单进程令牌桶，并用可控时钟手动推进时间。

## 先看一个具体问题

一个订单查询接口最多想承受每秒新增一个请求的长期流量，但允许短时一次放行两个请求。早上刚开始的三个请求同时到达，第三个要等多久才能再试？

### 通俗解释

门口的盒子装两张票，每一秒补一张，装满为止。每放行一个请求就用掉一张。空盒时返回还要等多久。盒子的容量控制突发量，补票的速度控制长时间平均速度。

### 正式概念

- **容量**是能保存的最大令牌数。桶满时，后续产生的令牌作废。
- **补充间隔**是产生一个新令牌需要的时间。本例每 1000 毫秒补一个，刻度从创建时开始。
- **单调时钟**只向前走，用来计算经过的时间。这里通过 `LongSupplier` 注入时钟，测试直接改时间。
- **临界区**保护读取时间、补充、检查和扣减。多个线程共用同一份状态。
- **令牌桶与并发限制**管的是不同量。前者管放行速率与突发，后者管同时在处理的请求个数。

## 完整示范

按 [macOS 运行指南](../docs/macos.md) 运行本题。程序会打印 `t=250ms 拒绝，等待 750ms`。`--goal` 再测试补充上限、时钟倒退和并发。

| 创建后经过 | 请求 | 令牌变化 | 结果 |
| --- | --- | --- | --- |
| 0ms | 第 1 个 | 2 → 1 | 放行 |
| 0ms | 第 2 个 | 1 → 0 | 放行 |
| 250ms | 第 3 个 | 0 → 0 | 拒绝，还要等 750ms |
| 1000ms | 再试 | 补 1，再扣 1 | 放行 |
| 8200ms | 新请求 | 最多补到 2，再扣 1 | 放行，还剩 1 |

打开 [RateLimitLab.java](src/cn/shiinapple/gateway/limit/RateLimitLab.java)，看 `clock.set` 怎样控制时间。到 [TokenBucket.java](src/cn/shiinapple/gateway/limit/TokenBucket.java) 看 `earned = elapsed / intervalMillis` 为何只加整数个令牌。余下的时间用取模保留。比如 8200ms 补完后，下一张票在 9000ms 出现。

## 独立练习

1. 改成容量 3、每 500ms 补 1。写一个时间表，验证 0ms 同时放 3 个、499ms 拒绝、500ms 放 1 个。
2. 为查询路由和导出路由各建一个桶。耗光查询的桶后，第一次导出仍可放行。用断言证明两个接口的突发额度彼此独立。考虑将不同租户映射到桶时，长时间不用的桶如何回收。

## 自测题

1. 容量 2 的桶每秒补 1 个，启动那一刻放了两个请求，是否说明实现超过了长期限速？
2. `sleep(1000)` 再发一个请求，为什么用于课堂时间边界测试容易不稳定？
3. 两台网关分别运行同样的令牌桶，集群会自然共用一份额度吗？

## 答案与解析

1. 没有。容量允许突发，补充速度决定长期平均新增配额。区分“开始时已有几张票”和“每秒新增几张票”。
2. 睡眠的线程实际何时被调度受机器负载影响，测试难以稳定踩到精确边界。可控时钟让 999ms、1000ms 都能重复。
3. 不会。本地状态各有一份。若要全局额度，需要共享额度或集中协调，还要决定协调服务不可用时的处理行为。

## 面试怎么讲

先说明保护对象，以及短时突发与长期速率各是多少。再解释若下游响应变慢，只用放行速率还可能积累很多在途请求。Nginx 负载均衡负责分发连接或请求，限流位置、计量范围和并发控制需要明确设计。
