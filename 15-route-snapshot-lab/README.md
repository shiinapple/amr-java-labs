# 15 · 路由热更新时，旧消息晚到怎么办？

对应简历里的**服务发现与动态路由**。课堂先聚焦全量配置发布和并发读写。

## 先看一个具体问题

网关把 `/orders` 转到 node-a。配置服务把它改到 node-c，发来版本 3。此时版本 2 的消息才到。如果回调收到消息就覆盖，流量会被送回旧节点。与此同时，已经开始处理的请求可能正在读取上一份配置。

### 通俗解释

想象前台每天换一张完整的值班表。每张表有编号，过期表不能把新表换掉。接待某位访客时，前台拿着同一张表完成查询。下一位访客重新拿表，能看到更新后的安排。

### 正式概念

- **全量快照**包含当前所有路由。能从版本 1 直接切到版本 3，因为 3 自带完整状态。
- **原子发布**用一次引用赋值切换整张表。快照不可变，持有旧引用的读者可以继续读取。
- **可见性**由 `volatile` 提供。写线程用 `synchronized` 同时保护版本判断和发布，避免两次写入相互穿插。
- **请求级一致性**要求一条请求拿一次快照并在后续查找中复用它。

## 完整示范

按 [macOS 运行指南](../docs/macos.md) 运行本题。基础输出是 `版本 3`。`--goal` 还验证下线空表、拷贝输入和并发写入。

| 事件 | 路由表当前值 | 之前已拿到 v1 的请求 |
| --- | --- | --- |
| 发布 v1 | v1 → node-a | 持有 v1 |
| 发布 v3 | v3 → node-c | 持有 v1 |
| v2 晚到 | v3 → node-c | 持有 v1 |
| 新请求开始 | v3 → node-c | 两条请求各用各的版本 |

先读 [RouteSnapshotLab.java](src/cn/shiinapple/gateway/routing/RouteSnapshotLab.java) 中的主流程。再读 [RouteTable.java](src/cn/shiinapple/gateway/routing/RouteTable.java) 的 `Snapshot`、`replace` 和 `snapshot`。在 `raceUpdates` 里，两个写线程等到同一个开始信号，分别提交 v6 和 v7。谁先执行都可以，最后必须留下 v7。线程闩锁用于测试时制造竞争，无需用 `sleep` 猜时间。

## 独立练习

1. v1 有 `/orders` 和 `/users`，v2 删除 `/users`。拿着 v1 的读者仍能找到用户路由，新读者查到为空。要求两处断言同时通过。
2. 画出两个写线程仅使用 `volatile` 时导致版本倒退的顺序。再写一个线程测试，用两个闩锁强制出现“v2 已通过比较、v3 已发布、v2 再写入”的顺序。用这组证据说明为什么要让比较与发布在同一临界区。

## 自测题

1. 如果版本 3 只是一条增量事件“把 `/orders` 改为 node-c”，还可以跳过版本 2 吗？
2. `volatile` 能解决什么问题？它能单独保证版本比较和替换一起完成吗？
3. 已经读到 node-a 的请求，路由切换后怎样安全下线 node-a？

## 答案与解析

1. 增量可能只表达局部变化。如果 v2 新增了 `/users`，跳过它会丢路由。判断线索是事件包含完整状态还是变化量。增量协议通常需要检查连续版本或补拉全量。
2. 它提供引用更新的可见性。比较和赋值仍是两个动作，两个写者都可能通过比较。这里固定用同一把锁把它们变成一个操作。
3. 发布新表后，新请求可以切到新节点。旧节点要等在途请求完成或达到下线路径规定的超时，再结束服务。这是连接和流量生命周期管理，课堂只验证路由表切换。

## 面试怎么讲

先问清配置消息是全量还是增量，再讲版本单调、写入原子性和请求内一致性。服务发现提供可用服务信息，动态路由把入口映射到目标。可以追问：配置订阅中断后，网关靠什么重新对齐版本？
